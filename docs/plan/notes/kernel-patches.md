# Kernel patches we want (russ sends; dcfs keeps a fallback until each ships)

The running list of upstream kernel changes that dcfs would benefit from,
with the dcfs step that owns each and what dcfs does meanwhile. Started
2026-10-10 at russ's request ("Add that to the list of kernel patches we
want to do").

| # | Change | Why dcfs wants it | Owning step | Meanwhile |
|---|---|---|---|---|
| 2 | ext4: `EXT4_IOC_SET_TUNE_SB_PARAM` enabling casefold on a mounted filesystem without loading `sb->s_encoding`; the next readdir of a `+F` directory dereferences NULL in `utf8nlookup` | found by the suite; present in mainline (7.3-rc6) | 26.15 (report drafted, reproducer in `tools/kernel_bugs/ext4_casefold_tune/`) | the DISABLED_ check `casefold_tune_oops_test`; Phase 16 rejects casefold directories anyway |
| 3 | btrfs: `WARN_ON(inode->csum_bytes)` in `btrfs_destroy_inode` after a failed inode read of a directory whose item was updated only in memory (`index_cnt`/`csum_bytes` share storage since d9891ae28b0d) | spurious diagnostic; a reply to the open syzbot report | 26.15 (reply drafted, reproducer in `tools/kernel_bugs/btrfs_failed_inode_read/`) | `fault_recover`'s btrfs variant pins inodes; run-qemu.sh tolerates exactly that WARNING when the guest reports it |
| 4 | FUSE, under `FUSE_HANDLE_KILLPRIV_V2`: `fuse_setattr` drops `ATTR_KILL_SUID`/`ATTR_KILL_SGID` and `ATTR_MODE` (fs/fuse/dir.c:2340-2342 (Linux v7.3-rc7)) before `setattr_prepare`'s owner check. A write's privilege removal (`file_remove_privs`, a truncate's or chown's kill bits) therefore reaches the server as a SETATTR that sets nothing, which it cannot tell from `chown(path, -1, -1)` and which says nothing of the writer's `CAP_FSETID`. The fix: forward `ATTR_KILL_SUID` and `ATTR_KILL_SGID` as two new `valid` bits on every SETATTR, set exactly when the kernel's own `setattr_should_drop_suidgid` or `chown_common` asked for them; and keep `setattr_prepare`'s owner check (`inode_owner_or_capable`) for a non-`ATTR_FORCE` SETATTR before `ATTR_MODE` is dropped. | passthrough writes never reach dcfs, so the empty SETATTR is all dcfs learns of their privilege removal | 17.2, 17.2b, 17.2e | dcfs takes a SETATTR that sets nothing on a file open for writing as the write's removal (`SuidgidClearedByWrite`), and asks `/proc` (`CallerHasCapFsetid`) only after a REMOVEXATTR of `security.capability`. The patch closes all of the following, all pinned in `credentials.sh` or documented in design.md, and retires `CallerHasCapFsetid` and `BackingFile::capability_removed`:<br>– a non-owner's held `chown(-1,-1)` succeeds and clears (`sgid-other-chownheld`);<br>– root's held chown clears setgid without group execute (`sgid-root-chownheld`);<br>– root's or a CAP_FSETID holder's held chown of a file with capabilities keeps setuid (`setuid-root-capchownheld`, the unsafe direction);<br>– a non-owner's chown strips capabilities before EPERM (`capchown-other-strips-then-fails`, the owner check);<br>– the no-CAP_SYS_PTRACE loss (`setuid-root-capwrite-noptrace`);<br>– overridden credentials and stale io_uring credentials. |
| 5 | dcache: `__d_obtain_alias` prefers a connected alias and allocates an anonymous dentry only when none exists (as `d_find_alias` already prefers) | lets a handle open after an O_PATH name lookup return a connected fd with no identity change and no freeze protection: the shelved Phase 13 done right | 13.5 (much later) | handle opens stay disconnected; `/proc/<pid>/fd` shows `/` |
| 6 | FUSE: an INIT opt-in to receive `FUSE_DESTROY` synchronously at unmount for plain `fuse` mounts, as `fuseblk` and virtiofs do, so a daemon that completes its shutdown in the DESTROY reply makes `umount` return after it has finished | removes the need for `umount.fuse.dcfs` and the per-mount lock file; closes the restart race at the source (russ, 2026-10-10: "During unmount, does FUSE not give the daemon a callback that blocks the unmount?") | 15.6d (new) | the 15.6b helper and lock; the helper becomes the fallback for kernels without the flag; also removes the no-fusectl limitation (a mount right after an unmount can meet the earlier daemon still finishing: README, russ 2026-10-11 chose to document rather than reorder startup) |
| 7 | FUSE: `fuse_fileattr_set` updates the cached ctime after a successful FS_IOC_SETFLAGS/FS_IOC_FSSETXATTR, as `fuse_setxattr` and `fuse_removexattr` do (`fuse_update_ctime`) | a chattr through FUSE leaves the kernel's cached ctime stale until the attr timeout; found by the 2026-10-17 kernel-cache inventory | 26.40 | dcfs invalidates the inode's attributes itself before the ioctl reply (`notify_inval_inode`, attributes only) |
| 8 | FUSE: a `/dev/fuse` daemon opts into automatic submounts (an INIT flag setting `fc->auto_submounts`, today set only by `fs/fuse/virtio_fs.c`), so `FUSE_ATTR_SUBMOUNT` is honoured (`fs/fuse/inode.c:472`, Linux v7.3-rc4); plus libfuse support to set `fuse_attr.flags` (`lib/fuse_lowlevel.c` zeroes it today) | dcfs stubs become real submounts with their own `st_dev`, so `find -xdev`, `du -x`, `rsync -x` and `tar --one-file-system` stop at them as they do on the backing (russ, 2026-10-17) | 23.13 (question 4 of its design item 9(b)) | `ENOTSUP` inside a stub, for now (russ, 2026-10-17): the tools descend and get an error, which is loud rather than silent |
| 9 | `fcntl(F_SETFL, O_DIRECT)` on a passthrough FUSE file does not reach its backing file (fs/fcntl.c:37; sync passthrough keeps open-time behaviour, async follows the new flag; fs/backing-file.c:95-100,164-174). Fix: the kernel re-syncs the real file's flags on each I/O, as overlayfs does (`OVL_SETFL_MASK = O_APPEND|O_NONBLOCK|O_NDELAY|O_DIRECT`, fs/overlayfs/file.c:63; `ovl_change_flags` at :65, called at :163-167, v7.3-rc7); FUSE passthrough, or fs/backing-file.c for all users, can do the same before the backing I/O. dcfs cannot work around it: the backing file is the kernel's, and dcfs never sees the fcntl | a flag toggled after open leaves the backing unaware of O_DIRECT, so the file is not direct where the caller asked for it (Explore research, 2026-10-18) | 23.15 (dcfs's fallback) | 17.6 pins the current behaviour; 23.15 serves O_DIRECT itself on the non-passthrough path |
| 10 | passthrough writes remove privileges with the caller's credentials: a passthrough write reaches the backing file as the daemon (CAP_FSETID), so setgid on a setuid+setgid-without-group-execute file survives where a native write by the caller clears it. Send after the other patches (`docs/design.md`, "FUSE-only machinery is a fallback with an expiry") | the mode is the one dcfs cannot pass through safely, so it must decline passthrough and do the write itself, with the caller's credentials | 23.17 (deferred until the production kernel carries this patch, likely years) | dcfs declines passthrough for that mode (`PassthroughFor`, dcfs/dir_cache_fs.cc:119; `docs/design.md`, "Caller credentials") and writes it as the caller |
| 11 | FUSE passthrough has no `.fadvise` or readahead forwarding: `posix_fadvise(POSIX_FADV_WILLNEED)` and `readahead(2)` on a passthrough file read ahead into the FUSE inode's own page cache (never used) through `fuse_readahead`, which sends FUSE_READ to the server. The patch forwards fadvise and readahead on a passthrough file to the backing file, as the backing_file ops already do for read, write and mmap | a passthrough file's readahead costs the daemon a FUSE_READ it never needed, and the data lands in a cache the file never reads (2026-10-18, from 23.16's review and russ's "do what the backing does") | 23.19 Readahead hints reach the backing (queued, not started) | workaround planned: on a READ for a passthrough handle, `posix_fadvise(WILLNEED)` on the backing fd for the range (not in the tree) |

Rules for the list: a reproducer in the tree for each bug (2, 3 have one;
4 gets one with 17.2; 5, 6 and 8 are features and get a test that detects
the kernel's support and exercises the dcfs path both ways); the draft
mail or patch in `docs/plan/notes/` before russ sends; after it ships,
the dcfs step that negotiates or detects it, keeping the fallback.

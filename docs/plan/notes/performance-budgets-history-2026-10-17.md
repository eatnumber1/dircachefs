### Performance Regressions and Findings Caught by Budgets and Cost Reports

1. **2026-10-06 / 2026-10-07 — Cached directory listing was 27× slower than the backing filesystem, caused by per-entry attribute queries, excessive read-ahead, and stepping past single-row lookups** — Caught by the [Phase 10 benchmarks] (`f03e108`, [`log.md:395`]), and then quantified and bounded in Step N4 by in-process SQLite step counters and statement budgets in [`test/qemu/guest/syscall_budgets.txt:33`] and [`ReaddirWorkTest`] (`ab5e4a5`, `2bc97ad`, `8b9b819`, `4cdc8dd`) — **Would an exact count of FUSE requests / backing syscalls / fsyncs / SQL statements have caught it?** Yes (exact SQLite statement step counts in `ReaddirWorkTest` and `warm-readdir sql_stmts` in `syscall_budgets.txt` directly caught each optimization: `ListDir` attribute join reduced steps from 31 to 21, read-ahead batching reduced steps from 250 to 140, and `ReadOne` reduced steps across all operations) — **Would a slope test?** Yes (`ReaddirWorkTest` is an explicit slope test bounding steps by $a \cdot N + b$ at $N = 100$ and $N = 1000$) — **Would an A/B wall-clock benchmark?** Yes on an idle host (the initial 27× gap was exposed by [`bench/dcfs_bench`]), but flaky under competing host load — **[certain]**

2. **2026-10-07 — High per-operation backing syscall cost on cold operations (create: 26, chmod: 24 backing syscalls, including unexpected reads of `security.capability` and `posix_acl_access`), and generation read after `name_to_handle_at`** — Caught by Step 26.3 golden strace traces and Step 26.4 backing syscall budgets in [`test/qemu/guest/syscall_budgets.txt:10-86`] (`44da625`, `340e333`; [`26-bumpers.md:60-65`]) — **Would an exact count of FUSE requests / backing syscalls / fsyncs / SQL statements have caught it?** Yes (exact count of backing syscalls and procfd syscalls per op in `syscall_budgets.txt`) — **Would a slope test?** Yes (for multi-operation workloads) — **Would an A/B wall-clock benchmark?** Unlikely (individual syscall overhead of 1–2 µs is indistinguishable from scheduling jitter in wall-clock benchmarks) — **[certain]**

3. **2026-10-07 — File creates executed a durable SQLite transaction with a WAL fsync on every single file ($1 \cdot N + 1$ fsyncs for $N$ creates), violating the design promise that a burst of creates costs only one WAL fsync per sync point** — Caught by Step 26.4b slope test [`SlopeTest`] in [`//dcfs:dir_cache_fs_slope_test`] (`45dcee8`; [`26-bumpers.md:94-97`]; leading directly to Step 23.11 "born-dirty create") — **Would an exact count of FUSE requests / backing syscalls / fsyncs / SQL statements have caught it?** Yes (exact count of WAL fsyncs / durable transactions per create: `create sync 2` in [`syscall_budgets.txt:41`]) — **Would a slope test?** Yes (it was specifically revealed by `SlopeTest.CreateSlope` measuring durable transactions across $N = 100$ and $N = 1000$) — **Would an A/B wall-clock benchmark?** Likely on physical storage (5 ms per create in `destroy_test`), but completely invisible in test guests where `/cache` sits on tmpfs and fsync latency is 0 ms — **[certain]**

4. **2026-10-08 — Addition of `StillWritable` read-only check after `syncfs` added an extra `fstatvfs` (observed as `fstatfs`) backing syscall to `fsync`** — Caught by [`test/qemu/guest/syscall_budgets.txt:75`] (`fsync backing` count rose from 11 to 12; commit `1541d0b`, [`log.md:2403`]) — **Would an exact count of FUSE requests / backing syscalls / fsyncs / SQL statements have caught it?** Yes (caught directly by exact backing syscall count in `syscall_budgets.txt`) — **Would a slope test?** No (fixed 1-call overhead per sync point) — **Would an A/B wall-clock benchmark?** No (one ~1 µs `fstatfs` call cannot be resolved above benchmark noise) — **[certain]**

5. **2026-10-09 — Inode access-time tracking added an extra `SELECT` to cold read-only opens (checking if a row is already dirty before taking a write transaction) and a timestamp update to directory listings** — Caught by [`test/qemu/guest/syscall_budgets.txt:33,86`] (`read sql_stmts` 20 -> 21, `warm-readdir sql_stmts` 13 -> 14; commits `a69f761`, `1535e6d`, [`log.md:1954`]) — **Would an exact count of FUSE requests / backing syscalls / fsyncs / SQL statements have caught it?** Yes (exact count of statement steps in `syscall_budgets.txt`) — **Would a slope test?** No (fixed statement overhead per operation) — **Would an A/B wall-clock benchmark?** No (a single in-memory SQLite statement step takes ~10 µs; undetectable) — **[certain]**

6. **2026-10-09 — Step 23.11 born-dirty create eliminated create WAL fsyncs (`create sync` 2 -> 1, `sql_stmts` 119 -> 116), but added an extra statement to check the directory's mutation mark on listing inserts (`cold-lookup sql_stmts` 37 -> 38)** — Caught by [`test/qemu/guest/syscall_budgets.txt:15,41`] and [`SlopeTest`] (cold lookup steps $20N + 16 \to 20N + 17$; commit `61f6a02`, [`log.md:2403`]) — **Would an exact count of FUSE requests / backing syscalls / fsyncs / SQL statements have caught it?** Yes (exact counts in `syscall_budgets.txt` caught both the reduction in `create` and the increase in `cold-lookup`) — **Would a slope test?** Yes (`SlopeTest.ColdLookupSlope` caught the extra step per entry) — **Would an A/B wall-clock benchmark?** Likely for the fsync elimination on physical storage, but impossible for the single lookup statement addition — **[certain]**

### Budget Failures That Were Noise (Load, Timers, Test Changes)

1. **2026-10-07 — `readdir_boundary.sh` wall-clock duration limit**
   - *Failure*: An absolute wall-clock threshold of 2.5 s for listing 6,000 files failed under host load at 3.20 s, 2.98 s, and 3.04 s ([`test/qemu/guest/readdir_boundary.sh:14-25`]).
   - *Fix applied* (`ab5e4a5`): Replaced absolute wall-clock duration with a ratio of daemon CPU ticks (4N entries vs N entries, bounded at 8×) and deterministic in-process SQLite step counting in [`ReaddirWorkTest`].

2. **2026-10-10 — Per-operation CPU time budgets in `cpu_budgets.txt` (`request_counts_test`)**
   - *Failure*: In Step 26.17b, individual operation CPU budgets (`ls-l-100`, `find-tree`, `stat-deep-10`, `cat` taking 1 to 20 ms) varied up to 2.4× across quiet runs from cache misses or interrupts, and under load reported 0 to 5 µs due to vCPU scheduling. Failed on its very first try on a loaded host ([`test/qemu/README.md:1297-1309`]).
   - *Fix applied* (`e8af8ac`): Dropped per-operation CPU budgets completely from [`test/qemu/guest/cpu_budgets.txt`], relying exclusively on deterministic FUSE request counts in [`request_budgets.txt`].

3. **2026-10-10 — `readdir_boundary_test` write-side I/O in `io_budgets.txt`**
   - *Failure*: The test ran 19 s alone and up to 40 s under load with ext4 on a host disk. Ext4 commits its journal every 5 s and dcfs syncs every 5 s (`--sync_interval_sec`), causing disk writes to scale directly with wall time (62 to 115 writes, 27 to 39 flushes) rather than test work ([`test/qemu/guest/io_budgets.txt:93-100`], [`test/qemu/README.md:1445-1452`]).
   - *Fix applied* (`b74caf9`): Excluded write-side metrics from [`io_budgets.txt`] for `readdir_boundary_test`, budgeting only read metrics (`reads`, `sectors_read`, `dcfs_reads`).

4. **2026-10-17 — Block-layer request merging causing `writes` budget failures in `request_counts_test` and `fault_backing_test_ext4`**
   - *Failure*: `request_counts_test` completed writes rose from 62 to 70 (or 68/69) against a budget of 62; `fault_backing_test_ext4` completed writes rose from 378 to 396 against a budget of 378 (`6aa8df5`, [`log.md:3588, 3708-3715`]). The Linux block layer merges adjacent write requests depending on queue timing and disk processing speed; field 5 of `/sys/block/<disk>/stat` counted only completed requests after merging.
   - *Fix applied* (`6aa8df5`): Modified `cost_sum_disk_stats` in [`test/qemu/guest/cost_lib.sh`] to sum completed plus merged requests (fields 1+2 for reads, 5+6 for writes: requests *issued*). Re-measured `reads` and `writes` in [`io_budgets.txt`] as requests issued (259 issued in 60/60 runs).

5. **2026-10-17 — SMT / hyperthread contention stretching `backing_test` CPU budget**
   - *Failure*: `//dcfs:backing_test` used 1.02 s CPU against a budget of 0.509 s (with 100% tolerance = 1.018 s) during a run with 51% host CPU pressure. 100 runs on a starved host ranged from 0.26 to 1.0 s ([`log.md:3715, 3727`], [`test/qemu/README.md:1313-1315`]).
   - *Fix applied* (`2179afa`, `816f150`, Step 26.36): Updated [`test/qemu/scripts/run-qemu.sh`] to detect host CPU pressure >= 20% and declare the run `load-starved`; CPU budgets are automatically unheld on load-starved runs (`budget_unheld_reason`).

6. **2026-10-17 — Missing sanitizer command-line arguments in `qemu_cc_test`**
   - *Failure*: In CI run 39046531637, `//dcfs:backing_test` under ASan spent 1.027 s CPU and failed its budget because [`qemu_cc_test.bzl`] omitted `--cmdline dcfs_sanitizer=...`, causing the harness to hold the ASan build to the plain build's budget (`233baa3`, [`26-bumpers.md:1169-1178`]).
   - *Fix applied* (`233baa3`, `d0c51c8`): Updated `qemu_cc_test.bzl` to pass `sanitizer_args()` and added [`dcfs/sanitizer_cmdline_test.cc`].

7. **2026-10-17 — Timed workload duration loop in `xfstests_1_test_ext4` (`generic/364`)**
   - *Failure*: `xfstests_1_test_ext4` failed `writes` (57,097 vs 21,437), `flushes` (15,620 vs 8,950), and `dcfs_writes` (14,896 vs 11,906) in CI. The shard runs `generic/364`, which executes a direct-write and fsync loop for `timeout 10s`. On CI's fast runner it issued 45,012 writes in 10 s; on a loaded local machine (load 36) it issued only 853 to 1,060 writes (`233baa3`, [`26-bumpers.md:1182-1205`]).
   - *Fix applied* (`233baa3`): Dropped all write-side lines (`writes`, `sectors_written`, `flushes`, `dcfs_writes`, `dcfs_write_bytes`) for `xfstests_1_test_ext4` in [`io_budgets.txt:48-58, 172-178`], keeping only read-side budgets.

8. **2026-10-17 — Ext4 journal commit timer firing during guest wall-time dilation in `write_test_ext4` and `fault_ace_b_test`**
   - *Failure*: Under 87–91% host pressure, `write_test_ext4` `writes` rose to 329–336 (budget 325) and `flushes` rose to 144–150 (budget 145); `fault_ace_b_test` counts ran 0.2% to 0.6% over budget. Because the guest clock runs while vCPUs wait for host scheduling, ext4's 5 s journal commit timer (`commit=5`) fired more times during prolonged runs, generating extra disk writes that dcfs did not issue ([`load-agnostic-tests-2026-10-17.md:99-116`], [`test/qemu/README.md:1369-1374`]).
   - *Fix applied* (`816f150`): Documented in Step 26.36 audit (follow-up I / 11); proposed resolution is mounting test disks with long commit intervals or unholding journal-dependent counts under load starvation.

### Was Any Regression Caught ONLY by a Block-Layer I/O or CPU-Time Budget?

**No. There is not a single performance regression in the history of dcfs that was caught only by a block-layer I/O budget ([`io_budgets.txt`]) or a CPU-time budget ([`cpu_budgets.txt`]).**

In fact, neither [`io_budgets.txt`] nor [`cpu_budgets.txt`] ever caught any real regression or performance finding in dcfs at all. Every single failure of those budgets was noise caused by block-layer request merging, host hyperthreading/scheduling contention, timer-driven kernel journal writeback, test macro configuration bugs, or time-bounded workload loops.

All real performance regressions and findings in dcfs were caught by:
1. Exact deterministic counts of backing syscalls and FUSE requests ([`test/qemu/guest/syscall_budgets.txt`], [`test/qemu/guest/request_budgets.txt`], [`test/qemu/guest/bench_write.sh`]).
2. Exact deterministic counts of SQLite statement steps and transactions ([`test/qemu/guest/syscall_budgets.txt`], [`dcfs/testonly/step_counter.h`], [`dcfs/testonly/cost_counter.h`]).
3. Slope tests parameterized over operation counts $N$ ([`SlopeTest`], [`ReaddirWorkTest`]).
4. Targeted side-by-side cost attribution tooling ([`test/qemu/scripts/xfstests_costs.py`]).

# Spare-disk trial, first run (2026-10-11)

russ ran the server side on his production file server with an agent of
his own, from the minimal runbook (the daemon binary called through a
`mount.dcfs` symlink, foreground, no helpers installed). Identifying
details (hosts, addresses, disk labels, ids) are left out: this file is
public.

## Server side (reported by russ's agent)

- Kernel: the distribution's HWE kernel, 7.0 series, booted for dcfs's
  6.9+ requirement (FUSE passthrough, `FS_IOC_GETFSUUID`).
- Backing: one physical 11 TB disk, 99% full, mounted by the system at
  its usual path; dcfs in the bind form over it with the cache database
  on an always-on disk:
  `mount.dcfs -o dcfs.fstype=bind,dcfs.cache_db=<always-on>/<disk>.db,dcfs.foreground,dcfs.stderrthreshold=0 <disk-mount> /tmp/trial/mountpoint`.
- Warm-up: a full `find -ls` over the mount, with the disk active.
- Spin-down: the vendor's power-control tool put the disk in standby; a
  spin-state monitor ran throughout.
- **Metadata-only work (`ls -R`, `find`, `stat`, `df`): the disk stayed
  in standby.** The agent's words: "The cache performed flawlessly without
  waking the drive."
- **One 1-byte read (`head -c 1`): the monitor saw the disk go from
  standby to active at once.** Passthrough wakes the disk on data access,
  as designed.
- NFS: the dcfs mount was bind-mounted to an export directory and
  exported read-only (`sync,no_subtree_check,insecure,all_squash,mp`, a
  fixed anonymous uid/gid, one client address) for the client leg.

## Client side (this machine, an agent of the orchestrator's)

Stages: mount over NFS 4.2; remote metadata work with the disk in
standby (`ls -R`, `find`, `stat` over NFS, the NFS client's counters
showing no READ); one file read, which must wake the disk; the warm
restart (dcfs stopped and started on the server, the first `find` fast).
Results are appended below as the stages run.

Stage 1: the server is NFSv4-only (no rpcbind, so `showmount` cannot
answer) and exports under the v4 pseudo-root; `mount -t nfs -o
ro,vers=4.2 <server>:/<export> /mnt/dcfs-test` worked first try (hard,
tcp, 1 MiB rsize); five top-level directories, no errors.

Stage 2 (disk in standby at the start; **the server's monitor saw it
stay in standby throughout**, russ relaying): remote metadata only.
`ls -R` of the whole tree: 18.3 s wall (174,869 files). `find -type f`
right after: 0.7 s (the client's caches warm). `stat` of all 174,869
files: 2 min 50 s, no errors. NFS client counter deltas: READ 0, OPEN 0,
CLOSE 0; GETATTR +77,043, LOOKUP +102,464, READDIR +6,867, ACCESS
+6,812; 193,189 RPCs, no retransmits. Two things the client saw: the
directory that is a btrfs subvolume of the backing (the snapraid content
subvolume in this layout) answers readdir with errno 524 on the client
(`ENOTSUPP`: dcfs serves a subvolume boundary as a stub whose contents
are ENOTSUP, and NFSv4 carries that as NOTSUPP; expected by design,
unfriendly over NFS, a documented limitation until 15.4 finishes the
stub behaviour); a snapshot directory and one data directory are
`Permission denied` under the export's all_squash uid, as expected.

Stage 3 (disk in standby): one 2.5 KB file read over NFS, one READ RPC,
10.6 s wall with no CPU: the spin-up wait. Passthrough reached the disk
exactly once, for data. Between stages 2 and 3, while the client was
idle, 63,443 GETATTR calls arrived at the server from this client with no
LOOKUP, READDIR or READ: something on the client host (an indexer or a
periodic scanner) revalidated the cached tree; the disk stayed in standby
through it, which is the point, but it is the kind of background
metadata traffic dcfs exists to absorb and worth naming.

Before the restart: one process on the client held a file descriptor (a
2.2 KB file, 64 bytes read) and a directory descriptor open. The server
then unexported, unmounted the export bind, stopped dcfs (Ctrl-C), started
it with the same command, re-bound and re-exported (the disk was spinning
from the earlier reads, so no spin-up timings here).

Stage 4 (after the restart, same client mount): the held descriptors
returned the right bytes (hash equal) and the same directory names, but
the NFS counters show no READ went out, so the client's page and dentry
caches answered and this proves nothing about handle survival. **Every
request that had to reach the server failed with EIO**: fresh opens of
three files, a LOOKUP of a nonexistent name (ENOENT expected), per-entry
attributes; cached listings still worked (`ls -R` 1.5 s, `find` 0.3 s,
same 174,869 files). Diagnosis: knfsd's export cache still mapped the
export's fsid to dentries of the FUSE superblock that no longer existed;
our own QEMU NFS test restarts dcfs under an export and passes only
because its harness runs `exportfs -f` afterwards. Stage 5 (below) tests
that.

Design candidate from this (not queued; for the list the trial reorders):
a daemon restart is a new superblock, so knfsd's handles, the export bind
and clients' state all point at a dead one, and no handle stability inside
dcfs can help. A daemon that keeps its `/dev/fuse` descriptor across
restarts (systemd's file-descriptor store, or handing the descriptor to
its successor) would resume the same connection and superblock, making
restarts, upgrades and crash recovery invisible to NFS clients and to held
descriptors.

Stage 5 (after `exportfs -f` on the server, a fresh client mount): the
mount succeeds, every operation still EIO, even the root listing.

Stage 6 (splitting client from server): no NFS client messages in the
client's kernel log; no lingering client superblock (`/proc/fs/nfsfs`
empty while unmounted); a `nosharecache` mount on a new mountpoint fails
identically; a packet capture shows the RPCs leaving and the server
answering compounds on the export's root handle with NFS4ERR_IO (five
such replies during the mount itself, which still succeeds; then the
user operations). **Server-side.** The README's own NFS section says
`exportfs -f` is enough after a restart ("nfsd's export cache holds a
reference to the old mount and answers EIO until it is flushed"), and
the QEMU NFS test passes with it; on the production server it was not
enough. Open at the end of the day: what knfsd resolves the root handle
to after the restart (the re-bound export directory, the old superblock
through a leftover reference, or dcfs answering EIO), to be read from the
server's dcfs log (do LOOKUP/READDIR requests arrive?), `exportfs -v`,
`/proc/fs/nfsd/exports` and the kernel log, and a local `cat` through the
dcfs mountpoint on the server.

Resolution: the server's local read through the dcfs mountpoint worked;
`findmnt` showed the export directory as a `fuse.dcfs` mount, and `ls`
on it gave "Transport endpoint is not connected": **the export was a bind
mount of the old FUSE superblock**, which the bind had kept alive when
the daemon was stopped, so knfsd served a dead filesystem and no flush
could change what the export path resolved to. The daemon was never at
fault. After the server unexported, unmounted the bind, remade it on the
new dcfs mount, re-exported and flushed: Stage 7 on a fresh client mount,
all checks pass: both file hashes equal the server's local reads, ENOENT
for a missing name, the directory's 8 entries with attributes, the stub
directory back to its 524, `ls -R` 21.4 s cold on the client (the disk
was spinning), READ +2 for the two hashed files, no ESTALE, no EIO.

## What the first run established

- Metadata-only work, local and over NFS from a client (175k files,
  193k RPCs), leaves the disk in standby. One data read wakes it.
- A daemon restart under an NFS export: dcfs comes back and serves, but
  **if the export is a bind of the dcfs mountpoint, the bind must be
  unmounted before the daemon stops and remade after**, or it keeps the
  dead superblock and knfsd serves EIO; `exportfs -f` alone is not
  enough in that shape. The README states the mountpoint-is-the-export
  case only; the QEMU NFS test covers that case only. Both change (15.12).
- Handle survival across the restart was not shown: the client's caches
  answered the held descriptors, and the restart's bind problem masked
  everything else. A clean retest needs the bind sequence right and a
  held descriptor whose next read must go to the server (a file larger
  than the client's read-ahead, read past the cached part).
- A directory that is a btrfs subvolume of the backing shows as errno 524
  to NFS clients (the stub's ENOTSUP through NFSv4): unfriendly; 15.4.
- Background metadata traffic from an idle NFS client (63k GETATTRs in a
  few minutes from an indexer or scanner) is real and dcfs absorbed it.

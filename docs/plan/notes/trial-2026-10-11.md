# Spare-disk trial, first run (2026-10-11)

russ ran the server side on his production file server with an agent of
his own, from the minimal runbook (the daemon binary called through a
`mount.dcfs` symlink, foreground, no helpers installed). Identifying
details (hosts, addresses, disk labels, ids) are left out: this file is
public.

## Server side (reported by russ's agent)

- Kernel: the distribution's HWE kernel, 7.0 series, booted for dcfs's
  6.9+ requirement (FUSE passthrough, `FS_IOC_GETFSUUID`).
- Backing: one physical 11 TB disk, 99% full, mounted by the system at
  its usual path; dcfs in the bind form over it with the cache database
  on an always-on disk:
  `mount.dcfs -o dcfs.fstype=bind,dcfs.cache_db=<always-on>/<disk>.db,dcfs.foreground,dcfs.stderrthreshold=0 <disk-mount> /tmp/trial/mountpoint`.
- Warm-up: a full `find -ls` over the mount, with the disk active.
- Spin-down: the vendor's power-control tool put the disk in standby; a
  spin-state monitor ran throughout.
- **Metadata-only work (`ls -R`, `find`, `stat`, `df`): the disk stayed
  in standby.** The agent's words: "The cache performed flawlessly without
  waking the drive."
- **One 1-byte read (`head -c 1`): the monitor saw the disk go from
  standby to active at once.** Passthrough wakes the disk on data access,
  as designed.
- NFS: the dcfs mount was bind-mounted to an export directory and
  exported read-only (`sync,no_subtree_check,insecure,all_squash,mp`, a
  fixed anonymous uid/gid, one client address) for the client leg.

## Client side (this machine, an agent of the orchestrator's)

Stages: mount over NFS 4.2; remote metadata work with the disk in
standby (`ls -R`, `find`, `stat` over NFS, the NFS client's counters
showing no READ); one file read, which must wake the disk; the warm
restart (dcfs stopped and started on the server, the first `find` fast).
Results are appended below as the stages run.

Stage 1: the server is NFSv4-only (no rpcbind, so `showmount` cannot
answer) and exports under the v4 pseudo-root; `mount -t nfs -o
ro,vers=4.2 <server>:/<export> /mnt/dcfs-test` worked first try (hard,
tcp, 1 MiB rsize); five top-level directories, no errors.

Stage 2 (disk in standby at the start; server's verdict on whether it
stayed there recorded below when relayed): remote metadata only.
`ls -R` of the whole tree: 18.3 s wall (174,869 files). `find -type f`
right after: 0.7 s (the client's caches warm). `stat` of all 174,869
files: 2 min 50 s, no errors. NFS client counter deltas: READ 0, OPEN 0,
CLOSE 0; GETATTR +77,043, LOOKUP +102,464, READDIR +6,867, ACCESS
+6,812; 193,189 RPCs, no retransmits. Two things the client saw: the
directory that is a btrfs subvolume of the backing (the snapraid content
subvolume in this layout) answers readdir with errno 524 on the client
(`ENOTSUPP`: dcfs serves a subvolume boundary as a stub whose contents
are ENOTSUP, and NFSv4 carries that as NOTSUPP; expected by design,
unfriendly over NFS, a documented limitation until 15.4 finishes the
stub behaviour); a snapshot directory and one data directory are
`Permission denied` under the export's all_squash uid, as expected.

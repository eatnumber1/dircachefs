### Verdict
All three fixes are correct against their stated invariants. I found no regression that today's single thread can reach. The sync fix still has a hole that the model doesn't cover: writable opens. RemoveChild has the same stale-resolve gap that Rename had.

### Findings, ranked

**1. High (coroutines only; pre-existing, not closed by R4): a writable open can lose its dirty row too early.**
- **Where:** `dcfs/backing.cc:1370-1371` builds `keep` from `open_for_write` when ClearDirty runs, not at BeginSync. `dcfs/dir_cache_fs.cc:1184-1185`: Release erases the inode from `open_for_write_` and records fresh attributes, but never Touches the fill guards. ClearDirty's `CanFill` test (`metadata_cache.cc:1318`) therefore can't see it.
- **Scenario:** X is open for write and in the snapshot D. A sync point takes BeginSync, and syncfs starts. The kernel writes X through passthrough, possibly after syncfs began. The last close sends RELEASE, which records the new size and mtime as present and drops X from `open_for_write`. ClearDirty then finds X not in `keep` with `CanFill(S,X)` true, and deletes the row. A power loss can keep the database and lose the writes, and recovery has nothing to forget.
- **Second window:** `dir_cache_fs.cc:1679-1683`. A writable Create adds the inode to `open_for_write_` only after CreateChild's phase-3 refreshes and MakeBackingFile, which are suspension points. A whole sync point can run in that window and clear the non-durable MarkDirty row before the passthrough writes begin.
- **Why nothing caught it:** design.md and backing.h now state the invariant in general terms. `formal/README.md:165` lists writable opens as not modelled.
- **Fix:** make the end of writing an event the guards see, i.e. Touch at the last writable Release, or run its phase 3 as a Mutation. As a backstop, snapshot `open_for_write` in `SyncSnapshot` and keep the union of both sets. For Create, call `BeginWriting` (a durable phase 1 plus a Touch) right after the insert, as Open does.

**2. Medium (coroutines without the kernel directory lock): RemoveChild has the rename_stale_source gap. The agent's suspicion is right.**
- **Where:** `dir_cache_fs.cc:656` resolves the child, then `:667` runs `BeginRemove(parent, name, child.id)` with no check in between.
- **Scenario:** unlink(D/a) resolves a→X through a populate that can't be recorded. A concurrent rename(D/b→D/a) completes. The unlink's phase 1 marks X unknown and dirty, but unlinkat removes Y.
  - Y's attributes (nlink) changed with no phase 1. They stay "present", wrong and not dirty, which breaks the tri-state rule and CacheNeverWrong whenever Y has another link.
  - `SettleUnlinkedFile(X)` (`:700`) works on the wrong object.
  - If X's row has already been retired, phase 1's `MarkAttrsUnknown` fails, and the unlink returns ENOENT for a name that exists.
- **Why the model can't find it:** it doesn't model hard links or child rows.
- **Fix:** the same pattern as Rename. Take a `FillSnapshot` before LookupOrPopulate, have `BeginRemove(..., resolved)` check `CanFill` for the parent and the child, and retry. Add a `dir_cache_fs_test` case with the same hook placement as RenameStaleSourceTest.

**3. Medium-low (coroutines): Rename's retry is not a real retry.**
- **Where:** `dir_cache_fs.cc:743-788`.
- **Problem:** when both resolves are cache hits, the three attempts run back to back with no suspension point. Any mutation of either parent, the source or the destination that is in flight makes the rename fail with EAGAIN deterministically. For example: concurrent maildir-style renames into one directory, or a FUSE_WRITE from writeback on the source in the non-passthrough fallback. EAGAIN is not a documented rename(2) errno, and most callers won't retry.
- **Status:** safe, and acknowledged by the TODO. ListCached has the same pre-existing shape.
- **Fix:** make sure the coroutine phase file has an explicit step to wait on the overlapping mutation, rather than leaving it only as a code TODO.

**4. Low (test gap):** the model's actual counterexample is a mutation that *ends* during syncfs. It is tested only by calling BeginSync and ClearDirty by hand (`metadata_cache_test.cc`). `SyncPointKeepsAMutationInFlightDirty` covers only the in-flight case. The new harness could cover the real window: a `-Wl,--wrap=syncfs` hook that runs a full FUSE MKDIR during an FSYNCDIR's sync point, then checks the parent's and child's dirty rows.

**5. Low:** `ClearDirtyKeepsEverythingPastTheFloor` (`metadata_cache_test.cc:1279`) copies Touch's prune by hand. If the prune logic changes, the test won't follow. Consider making `kMaxTouched` a `FillGuards` field (a production setting) so the test can trigger a real prune cheaply.

**6. Low (performance):** BeginSync loads the whole dirty set. ClearDirty then issues one DELETE per row and searches `keep` linearly each time (O(|D|·|keep|)). That cost is paid even on today's single thread, where nothing can change.
- **Fast path:** if `seq == synced.fills.seq` and `inflight` is empty, nothing was added since BeginSync. MarkDirty only happens before its mutation's End moves `seq`. The old bulk delete-except-keep is then exact.
- **Prune note:** a prune during a sync window keeps every row. Under sustained load (65,536 or more distinct inodes touched per syncfs), the dirty set stops shrinking until the load ends. That is bounded, so this is only a note.

**7. Low (plan drift):** the fixes differ from what `docs/plan/review-fixes.md` R4 prescribes:
- re-check completeness after the syscalls (instead, the listing is taken right after the check);
- keep inodes in flight (instead, the CanFill snapshot);
- LinkDentry rollback for a hard link (instead, phase-1 verification).

The commit messages justify each change well, but the R4 text was not updated in the same change.

**8. Suspected, low:** under coroutines, Readdirplus's per-entry `EntryFor` runs after the listing snapshot. If a listed child's row is deleted during an earlier entry's refresh, the whole reply fails instead of skipping that entry. The old interleaved loop had similar exposure, so this is not a regression.

### What I verified by reading
- **(a) Sync:** a mutation's syscall happens between its phase-1 Touch and its End Touch. So `CanFill(S,id)` together with membership in D is exactly "the syscall returned before BeginSync". Inflight entries are never pruned, and a prune after S raises the floor above S. BeginSync runs immediately before the first syncfs, with only SQL in between. `dirty.any` is now computed from the table, which is correct. A kAborted phase 1 rolls back before RegisterMutation and `dirty.any` are set.
- **(a) Readdir:** IsDirComplete and ListDir now run with only SQL between them, and the callback does no I/O. Offsets, cursors and the budget accounting are equivalent to before. A recorded PopulateDirectory leaves no unknown rows: RecordChild links every listed name, refused names are set refused, and everything else is pruned. So "populate, then check again" cannot become a permanent EAGAIN today. The pagination code moved, so confirm that `test/qemu/guest/readdir_boundary.sh` ran.
- **(a) Rename:** a stale (parent,name)→id binding requires a mutation naming the parent, which Touches it. The check runs first inside phase 1's transaction. kAborted has no other source in the code. The backing layer starts no mutations, so the rename's own resolve cannot cause it to abort.
- **(c) Tests:** every failing-first test places its hook correctly.
  - Readdirplus: the `"."` refresh is the first open_by_handle_at, and d is complete.
  - Readdir: ParentOf runs with d's dentry removed.
  - Rename: the destination's populate runs after the source is resolved and before phase 1.
  - Each test asserts that its hook ran.
  - The wrap is link-time and confined to the test binary, test code stays in `*_test.cc`, and no production code paths were added for tests.
- **(d) Model:** R1 matches the code: `rsnap` is taken before the source resolve, retries match (3 tries in both), and only D is checked, which suits the single-inode abstraction; the code also checks the source and destination. ReaddirStep now serves its reply before the `"."` refresh. S1 and S2 match BeginSync and ClearDirty, and "D in snapshot" really is implied. Removing `SyncExclusive` is sound: it only adds behaviours, and today's atomic S1→S2 schedule is still among them. Dropping CacheNeverWrong from `tristate_f4`'s invariants removes nondeterminism; it doesn't weaken anything.
- **Not verified:** TLC results and state counts, MC_large and MC_liveness under the larger state space, and every Bazel run.

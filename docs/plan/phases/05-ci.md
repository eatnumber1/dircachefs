# Phase 5 — CI runs the QEMU suite

After Phase 3 (Drop the kernel patch; download and build the test kernel) the suite needs only a stock kernel, so GitHub-hosted runners
can run it (standard Linux runners expose `/dev/kvm`; verify, and add the
usual udev rule granting the runner user access).
- Platform (russ): GitHub Actions on GitHub-hosted runners.
- Workflow: `bazel test` the full matrix (ext4/xfs/btrfs) and the ASan
  configuration. The kernel, QEMU, busybox and Debian image are ordinary
  Bazel targets (Phases 3 and 4), so the workflow needs no separate build
  steps: it restores and saves Bazel's disk and repository caches
  (`actions/cache`), keyed so a pin change rebuilds only what changed.
  Upload test logs on failure. Replace today's build-only `ci.yml`.
- **Develop the workflow locally with `act`** (https://github.com/nektos/act;
  russ, 2026-10-06) before anything is published to GitHub: `act` runs the
  workflow's jobs in containers resembling GitHub's hosted runners, so the
  pipeline can be iterated on without pushing. Pin `act` like every other
  tool (fetched by Bazel as a release binary with sha256, under
  `third_party/act/`), and pin the runner image by digest. KVM is passed to
  the job container (`--container-options "--device /dev/kvm"`, with the
  right group), so QEMU tests run there as they would on a hosted runner.
- **Non-hermeticity detector.** The job container has only what a fresh
  runner has, not this machine's packages, so any build or test that
  quietly depends on a host tool or library (as QEMU's host zlib and the
  host mke2fs did in Phase 4) fails under `act`. A full `bazel test //...`
  under `act` is part of this phase's done criteria, and any host
  dependency it exposes is either made hermetic or listed, with its reason,
  in the README's host requirements (and installed explicitly in the
  workflow).
- Prerequisite on russ's machine: Docker 29 is installed, but russ is not
  in the `docker` group; `act` needs Docker access (`sudo usermod -aG
  docker russ` and a new login, or rootless Docker). Agents must not change
  group membership themselves: ask russ.
- Test first: a branch whose workflow runs one QEMU test and fails today
  (no KVM access / patched kernel required), then green.
- Kernel matrix (CI only; local runs use the pinned default kernel): CI
  runs the suite on the minimum supported kernel (the
  version README states) and on the latest stable release, each built by
  the same download-and-build script with the same config fragment.
- Without KVM the tests fall back to plain QEMU emulation (TCG); this
  already happens automatically (`run-qemu.sh`), but it is slow today
  (an e2e test ran past 600 s under TCG; unit tests get 60 s, e2e 1200 s).
  With a minimal kernel and no firmware it should not be (russ). Step
  5.1, before the workflow: measure every test under TCG
  (`DCFS_FORCE_TCG=1` or an unwritable /dev/kvm), boot with `printk.time=1
  initcall_debug` to see where guest time goes, and fix the causes found
  (candidates to check, not assumptions: single-threaded TCG with `-smp 2`
  -> `-accel tcg,thread=multi`; clocksource/TSC calibration with
  `pit=off`; entropy waits; `-cpu max` cost; kernel config). Target: each
  test within ~10x its KVM time; timeouts then set from the measurements.
  CI uses KVM when present and TCG otherwise, same scripts.
